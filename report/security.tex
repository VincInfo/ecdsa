\section{Security Risks}
The Elliptic Curve Digital Signature Algorithm (ECDSA) is a clever way of keeping our digital world secure. But, if we want to use ECDSA effectively, we need to pay attention to some of the challenges it brings, especially when it comes to how difficult it can be to implement because it's quite complex.

ECDSA's strength comes from the complicated math it is based on, and it uses smaller but tough-to-crack keys. This helps to save on data space. However, this complexity can also make ECDSA tough to put into practice. If not implemented correctly, it can easily lead to security issues.

In the following sections, we're going to explore two major challenges. We are going to explain the the potential pitfalls with bad random number generators, and the possibility of time-based attacks. We'll also provide possible solutions to mitigate these issues. Furthermore, we will present real-world examples of where such attacks have been successfully executed, providing a practical understanding of these concepts.

\subsection{Poor Random Number Generator}
The nonce, or a "Number used ONCE," is a crucial component of ECDSA and contributes a significant layer of security.\footnote{Starting out, ChatGPT was overly concerned with predictability of generated keys. This is still important, but it is not a unique problem of random number generators to ECDSA. We had to clarify the issues with bad nonces.} It must be unique and random for every signature to ensure the private key isn't revealed. However, the security of these nonces and, therefore, the overall encryption system heavily depends on the strength of the random number generator used. There are four key issues we need to consider while discussing the quality of random number generators for nonces: repetition, predictability, size and bias.

\subsubsection{Repetition}
\label{subsubsection:repetition}
Reusing a nonce in multiple signatures is a significant security flaw. Even though the messages signed might be different, the fact that the same nonce was used provides an attacker with a critical amount of information. With two signatures sharing the same nonce but different messages, the private key can be calculated.

To understand this, consider the ECDSA signature equation:\footnote{Surprisingly ChatGPT generated these mathematical equations correctly. Only the formating had to be adjusted to get nice looking equations.}

\begin{equation} \label{eq:1}
s = \frac{h(m) + r d}{k} \bmod q
\end{equation}

In this equation, \textit{k} represents the nonce, \textit{h(m)} is the hash of the message, \textit{d} is the private key, \textit{r} is the x-coordinate of the EC point \(r=kG\), and \textit{q} is the order of the elliptic curve's generator point \textit{G}. If the same nonce \textit{k} is used for two messages, \textit{m1} and \textit{m2}, resulting in two signatures \textit{(r, s1)} and \textit{(r, s2)}, notice that \textit{r}, the x-coordinate, is the same for both since the same \textit{k} was used.

This presents a problem as it allows any observer to calculate the nonce \textit{k} as:

\begin{equation} \label{eq:2}
k = \frac{h(m1) - h(m2)}{s1 - s2} \bmod q
\end{equation}

Once the nonce is known, the observer could afterwards calculate the private key \textit{d} using the private key equation:

\begin{equation} \label{eq:3}
d = \frac{s k - h(m)}{r} \bmod q
\end{equation}

This means that the reusing of nonces can lead to the exposure of the private key. Hence, it's crucial to ensure that nonces are unique and not reused when generating ECDSA signatures to maintain a secure system. This includes the use of a proper random number generator, that cannot produce the same number twice.

\subsubsection{Predictability}
If an attacker can predict the next number generated from a specific algorithm, it instantly voids the security of the cryptographic operations relying on that algorithm. ECDSA, in particular, relies on the randomness of the nonces generated. Predictable nonces can enable an attacker to reverse-engineer and reveal the private key with equation \ref{eq:3} in section \ref{subsubsection:repetition}. This vulnerability drastically undermines the effectivity of the ECDSA security protocol.

In parallel, the same principle applies to the generation of keys. Keys should ideally be unique and unpredictable. However, if the pseudo-random number generator used for the key creation is compromised, it results in a production of predictable keys, rendering the entire security protocol ineffective. An attacker could potentially predict future keys and gain unauthorized access to sensitive data. However this concept is not unique to ECDSA and is not further explored in this paper. A solution to this issue would be to use a random number generator that makes it impossible to predict its output.

\subsubsection{Size}
When nonce values are of small sizes such as 64-bit or 128-bit, they are susceptible to cryptanalytic attacks. One possible attack is using Pollard's rho algorithm to solve for these small nonces. The algorithm can determine the discrete logarithm—that is, find the nonce—in a number of steps proportional to the square root of the size of the group. 64-bit or 128-bit nonces are small enough for a targeted attack to be feasible \cite{cryptoeprint:2019/023}. The solution to this issue is to simply to use Nonces that are bigger, for example 256-bit.

\subsubsection{Bias}
\label{subsubsection:bias}
Sometimes there might be patterns or 'biases' in how the nonce is created. If these biases exist, they could potentially hint at what the nonce number is. If someone else can guess this nonce, they might infringe on our coded messages' security. Therefore, it is vital to understand these biases, their impacts, and how to avoid them in simple and practical terms. We will delve into this topic in the following section.

In the ideal scenario, each nonce generated in ECDSA should be randomly unique. This means that it does not correlate with any other nonce and has no recognizable patterns. Ensuring complete randomness means the security of the system remains intact. However, if a part of the nonce remains the same across different computations — say, the first few or the last few digits don't change — this introduces a bias. This is problematic because it gives an attacker something to work with. By analyzing multiple signatures and exploiting these consistencies, they could derive the private key using these biases in the nonce generation. This can be achieved with the Hidden Number Problem (HNP).

The HNP involves guessing a hidden number when you only have partial information or hints. Imagine you have a long number, but you only know some of the digits and the position of these digits in the number. The hidden part of the number would be the digits you do not know. The challenge of the HNP is to figure out these unknown digits \cite{cryptoeprint:2020/1506}.

Relating it back to our scenario, an attacker who can determine a part of the nonce due to a bias can use this knowledge as a 'hint'. If they can obtain multiple signatures that contain these weak nonces, they can create a system of equations satisfying the HNP. By solving these equations, they aim to discover the unknown digits. In literature there are two techniques to solve the HNP: Lattice-based techniques and Fourier analysis \cite{cryptoeprint:2019/023}. The following paragraphs will explain how the former technique is used for extracting a key from a bias in the nonces. Fourier analysis is more complicated but it is more useful for more samples and smaller biases.

In simple terms, a lattice is a grid formed by points in space. This grid is defined by a set of basis vectors. The main goal of lattice reduction is to find a new and shorter basis for the same lattice. When applied to the Hidden Number Problem, the aim is to use these simplified or reduced lattices to make the problem more manageable.

So, let's say we have a series of signatures with a bias in their nonce values making a part of each nonce predictable. These partial nonces, along with the known signatures and public key, can be used to create a lattice in multi-dimensional space. In this lattice the solution is represented as a short vector. This vector is known to be close to a lattice point but not exactly on it. To find this short vector, a Lattice Basis Reduction algorithm is used, such as Lenstra-Lenstra-Lovasz (LLL) algorithm \cite{cryptoeprint:2019/023}\cite{cryptoeprint:2020/1506}.

This results in a candiate value for the nonce and a possible private key can be calculated with the equation \ref{eq:3}. With this key the public key can be calculated and it can be compared with the actual public key. If the keys match, the private key is revealed \cite{cryptoeprint:2019/023}. More reading can be done on how the lattice is constructed in \cite{cryptoeprint:2020/1506}.

It should be noted, that a non-uniform distribution of the nonce generation can also introduce a bias that can be exploited with this technique. Also it's worth mentioning that biases in nonces or even similar nonces can result in multiple security risks which include two different actors being able to find out the private key of the other one with there own private key. How these risks work is outlined in \cite{cryptoeprint:2014/848}. Therefore it is crucial for the random number generator to be uniform.

\subsubsection{Examples}
The pitfall of repeated nonces has occured a few times in the past.\footnote{ChatGPT hasn't been used in this section because we wanted to use examples we found while researching.} At one point in the past, Sony used a fixed nonce to sign their software for the Playstation 3 \cite{cryptoeprint:2020/728}. Also the Java secure random generator had issues with the random number overlapping sometimes \cite{cryptoeprint:2017/1014}. As outlined in section \ref{subsubsection:repetition}, this allows for the private key to be calculated. In Sony's example this means that others could use the private key to sign their own software. Java's number generator was implemented in some Android applications. This resulted in the leackage of various keys of bitcoin wallets \cite{cryptoeprint:2014/848}.

The exploitation of biases in nonces, or even small nonces, is explored in \cite{cryptoeprint:2019/023}. Biases in nonces, and even small nonces, occure in faulty ECDSA implementations used in cryptocurrency transactions. These issues can be exploited and some adresses of cryptocurrency wallets where already compromised. This can be done as described in section \ref{subsubsection:bias}. There are a few categories the faulty nonce generation fall into. First, there are very small nonces with 32 bits or less. Most of these nonces appear to be handcrafted. The next category are small nonces ranging from 64-bit to 160-bit. Also 256-bit nonces that share 128-bit suffixes have been exploited to find the private key used to sign the transaction with these faulty nonces. Of course this could be expanded or modified to exploit even smaller biases \cite{cryptoeprint:2019/023}.

\subsubsection{Solution}
As seen in this section about nonce generation it's important the nonce doesn't leave any security risks. The solution to this issue is to use a cryptographically secure pseudorandom number generator. This ensures that the random number can't be predicted or backtracked, the values don't repeat and there is no bias in the numbers. Possible random number generators usable for proper nonce generation are EdDSA3 or RFC6979 \cite{cryptoeprint:2020/728}. This ensures there isn't any possible prediction, repetition or bias in the generated nonces. Using a random number generator that doesn't ensure these issues aren't a problem will leave a huge security risk to the application using this faulty implementation of ECDSA.

\subsection{Timing Attack}
One possible type of attack that can happen is a timing attack. This attack focuses on how long it takes for the algorithm to work. By studying the time it takes to process information, the attacker might be able to find confidential information that compromises the key. This section is based on \cite{cryptoeprint:2011/232} and will look at how this type of attack works on ECDSA and how it can be prevented. \footnote{ChatGPT mixed up what part of signing allows timing attacks.}

\subsubsection{Montgomery Ladder}
Before we look at the specifics of getting the key from a timing attack, we'll have to understand the Montgomery Ladder. It is a method used within ECDSA to carry out scalar multiplication, a key operation in elliptic curve cryptography. The primary advantage of the Montgomery Ladder is that it runs in constant time, meaning it doesn’t leak information about the scalar (or key) through timing attacks. It also has the benefit of being efficient.

The Montgomery Ladder operates using two points R0 and R1 on the curve, and these steps:

1. Initialize R0 to the point at infinity (the equivalent of '0' on an elliptic curve) and R1 to the point you wish to multiply.

2. Each bit 'b' of the scalar (from most significant to least significant) dictates the following operations:

    - If 'b' is 0, then double R0 and add R1 to R0.
    
    - If 'b' is 1, then add R0 to R1 and double R1.
    
3. By the end of this process, R0 will have the value of the scalar multiplication.

The security of this comes from its resistance to side channel attacks, since the steps are always the same for all bits of the scalar (making it difficult for an attacker to gain information about the scalar/key).
